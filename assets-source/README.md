# Tennis asset source contract

Authored sources are organized by tool; GLB is the tool-independent runtime
contract. New low-poly characters and suitable small/medium assets should use
committed `.bbmodel` sources in `blockbench/`, with source exports written to
`blockbench-exports/`. The accepted Phase 04 environment remains sourced from
`blender/TennisPortfolio.blend`, with source exports in `blender-exports/`.

```text
assets-source/
├── blender/                 # accepted Phase 04 sources and legacy/specialized work
├── blender-exports/         # Phase 04 source GLB exports
├── blockbench/              # preferred new .bbmodel authored sources
├── blockbench-exports/      # new source GLB/glTF exports
└── fixtures/                # deterministic pipeline/loader fixtures
```

Production derivatives belong in `public/models/`. Never hand-edit source exports
or production derivatives. `blockbench/player-a.bbmodel` and
`blockbench/player-b.bbmodel` are Phase 07 naming/pivot calibration templates;
the checked-in GLBs in `blockbench-exports/` are deterministic generated
calibration fixtures, not visually authored or manually exported Blockbench art.
They exist to verify the offline-to-web contract and must be replaced by reviewed
Blockbench exports before either player is approved as production artwork.
Do not move, delete, or regenerate the Phase 04 assets as part of the authoring-tool
migration.

## Names and partitions

| Source export | Runtime path | Required stable node prefixes |
| --- | --- | --- |
| `blender-exports/court.glb` | `/models/court.glb` | `ENV_Court_`, `ENV_Net_`, `LINE_` |
| `blender-exports/stadium-shell.glb` | `/models/stadium-shell.glb` | `ENV_Stadium_` |
| `blender-exports/props.glb` | `/models/props.glb` | `ENV_UmpireChair_`, `ENV_Benches_` |
| `blender-exports/scoreboard.glb` | `/models/scoreboard.glb` | `ENV_Scoreboard_` |
| `blockbench-exports/player-a.glb` | `/models/player-a.glb` | `CHAR_PlayerA_Root`, `BONE_`, `SOCKET_Racket` |
| `blockbench-exports/player-b.glb` | `/models/player-b.glb` | `CHAR_PlayerB_Root`, `BONE_`, `SOCKET_Racket` |

`CHAR_`, `PROP_`, `LIGHT_`, and `CAMERA_` names are reserved for later authored
exports. Runtime code must not depend on Blender's autogenerated object names.

## Shared coordinate and export contract

- Export standard Y-up glTF/GLB. Blender sources use meters and Z-up before glTF
  conversion; Blockbench scenes must export to the same application-space scale
  and orientation.
- Court center is application `[0, 0, 0]`; the court is 8.2m × 12.4m outer edge.
- The net runs along X at `z = 0`; north is positive Z.
- Moving character root bones are on the ground plane before export;
  tennis-ball origin is geometric center; racket origin is hand-grip attachment.
- Apply safe transforms, preserve stable authored names, and exclude cameras/lights
  unless deliberately exported. Runtime code must not depend on tool-generated names.

Player A faces **+Z** at its south baseline; Player B faces **-Z** at its north
baseline. Both source roots are `[0, 0, 0]` at ground level and are positioned at
the established `COURT_DIMENSIONS.playerBaselineZ` by the calibration-only loader.
There is no runtime scale correction. `SOCKET_Racket` is the left wrist/grip
attachment point in the current contract.

## Phase 07 character naming and manual Blockbench export checklist

Both players must keep this hierarchy exactly unless runtime and validation are
changed together: `CHAR_PlayerA_Root`/`CHAR_PlayerB_Root` → `BONE_Hips` →
`BONE_Spine`, with `BONE_Head`, `BONE_Arm_L_Upper` → `BONE_Arm_L_Lower` →
`SOCKET_Racket`, `BONE_Arm_R_Upper` → `BONE_Arm_R_Lower`, and the left/right
upper/lower leg chains under hips. Geometry leaves may use a unique `MESH_`
prefix; no unnamed, generated (`cube12`/`bone23`), or other semantic node names
are permitted. Phase 07 permits zero animation clips; Phase 08 clip names must
be explicit and stable.

For each genuine Blockbench player export:

1. Open the matching `.bbmodel` and replace the calibration template geometry with
   the approved faceted silhouette (500–1,500 triangles preferred, review above
   2,500; one material preferred, three slots maximum).
2. Keep the root at the ground plane, set the documented bones/socket pivots, and
   use Y-up glTF application coordinates. Place the racket grip origin at
   `SOCKET_Racket`; do not bake a corrective runtime scale or facing rotation.
3. Use material/vertex color first. If a texture is necessary, use a reviewed
   64/128/256px palette atlas; reserve nearest magnification only for intentional
   pixel maps and visually check minification/mips. Do not add KTX2/Basis without
   a source texture and a visual comparison.
4. Export static GLBs directly to `assets-source/blockbench-exports/player-a.glb`
   and `player-b.glb`, preserving node names and omitting cameras/lights. Do not
   hand-edit that export or its production derivative.
5. Run `pnpm assets:build:reviewed-characters`, then open `?debug=1` to mount the static calibration
   players at both baselines. Verify feet, scale, +Z/-Z facing, socket/grip, and
   source-versus-optimized appearance at the application camera distance.
6. Record visual approval before adding clips; Phase 08 alone may connect named
   clips to the narrative timeline.

## New Blockbench authoring contract

- Keep the editable `.bbmodel` as the source of truth and commit it according to
  repository asset policy.
- Use stable `CHAR_`, `PROP_`, bone, animation-clip, and socket names. Document any
  runtime-consumed names before integration.
- Prefer one skeleton, a small number of meshes/material slots, and the geometry
  and texture budgets in `docs/RETRO_ART_DIRECTION.md`.
- Place the character root on the ground plane and the racket socket/origin at the
  grip. Confirm scale, handedness, and animation orientation in the application.
- Export a source GLB/glTF to `blockbench-exports/`, then pass it through the
  repository optimization and validation path before copying any production GLB.
- Manually compare the source export and optimized derivative at the authored
  application camera distance. Do not claim an export or visual review occurred
  unless it was actually performed.

## Legacy Phase 04 Blender procedure

1. With Blender installed, run `blender --background --python
   assets-source/blender/create_tennis_portfolio.py`. This creates
   `TennisPortfolio.blend`, every Phase 04 root collection, and the four source
   exports under `blender-exports/`.
2. Build/import each partition with the exact stable object names above. Apply
   rotation and scale to static meshes; keep intentional prop pivots.
3. Export a calibration `court.glb` first. In the browser, it must overlay the
   primitive 8.2m × 12.4m court centered at origin with its net at `z = 0`.
4. Export only the named collection to its matching source path. Preserve mesh
   names; omit unused cameras, lights, and animation tracks.
5. Run `pnpm assets:build`. Compare the exported result at expected camera
   distance before introducing KTX2 textures.

This procedure remains supported for the accepted Phase 04 environment and
legacy/specialized work. Blender is not a prerequisite for ordinary new retro
character authoring.

`fixtures/calibration-glb/` contains deterministic low-poly environment fixtures
generated by `scripts/generate-source-assets.mjs`. `pnpm assets:fixtures` also
regenerates the Player A/B calibration fixtures, then rebuilds and validates all
six outputs; it cannot validate stale character derivatives. These fixtures test
the asset contract only and are not production art. The checked-in `/public/models`
currently derives from accepted `blender-exports/` plus fixture-labeled character
exports; verify the per-asset `sourceKind` entries after `pnpm assets:build`.

`pnpm assets:build:reviewed-characters` is the explicit provenance switch for
genuine, manually reviewed Blockbench exports. It records
`sourceKind: "blockbench-export"`; the default build intentionally records
`"blockbench-calibration-fixture"` for the checked-in generated player outputs.

## Budgets and compression

Each current Phase 04 environment partition is capped at 100KB, except
`scoreboard.glb` at 60KB.
`pnpm assets:build` runs glTF Transform inspect → prune → dedup → weld → high-level
Meshopt compression for static environment partitions, preserving stable node names
and validated application-space bounds. Drei's `useGLTF(..., false, true)` enables
the compatible Meshopt decoder at runtime. Calibration fixtures are texture-free;
reviewed `blockbench-export` player assets may use an embedded 64/128/256px PNG
palette atlas only. KTX2/Basis remains disabled until authored textures can be
visually reviewed.

New character budgets are defined in `docs/RETRO_ART_DIRECTION.md`; Player A and B
each have an 80KB production byte budget. The optimizer records source kind per
asset, runs `inspect → prune → dedup → Meshopt` for characters, and deliberately
does **not** weld them because a later skinned export could make that unsafe.
It must preserve skins, animation clips, pivots, sockets, and stable names.

## Runtime loading and failure contract

The court loads first and retains the primitive court as both its Suspense and
error fallback. Props load only after the court resolves or fails, scoreboard only
after props resolves/fails, and stadium last. Each decorative partition has an
independent error boundary with a null fallback, so a failed decorative request
cannot remove the initial interaction or block later partitions.
